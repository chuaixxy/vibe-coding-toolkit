# Vibe Coding 提示词生成

为用户生成可直接交给编程 Agent 的提示词。使用 **R-C-G-C-O-E** 六要素明确任务与验收方式。本 Skill 只生成提示词，不代替用户执行提示词中的开发任务。

## 收集任务信息

1. 识别真实场景：方案设计、功能实现、故障排查、测试、代码审查或它们的组合。保留用户指定的范围和工具。
2. 优先使用用户提供的事实。如果当前仓库信息对提示词有影响，只读取必要的项目规则、文档、代码和测试。示例不能当成项目事实。
3. 如果缺失的信息会明显改变任务方向，提出一个聚焦的问题；其他缺失信息使用明确占位符，例如 `[待填：现有 API 契约]`。不编造需求、规模、技术栈、运行命令、验证结果或故障根因。

## 组织提示词

使用用户的语言，按以下六要素写出可复制的提示词。简单任务可以合并或压缩栏目，但要保留必要信息。

| 要素 | 应写明的内容 |
| --- | --- |
| R — Role（角色） | 完成任务所需的专业视角；不使用没有实际作用的夸张头衔。 |
| C — Context（背景） | 已知系统事实、现有行为、输入材料和相关文件；区分事实与假设。 |
| G — Goal（目标） | 一个具体交付物，或有明确顺序的一组交付物。 |
| C — Constraints（约束） | 与任务相关的兼容性、改动范围、安全、依赖、性能和项目规则；不添加任意要求。 |
| O — Output Format（输出格式） | 用户需要的产物及呈现形式。 |
| E — Evidence / Evaluation（证据与评估） | 可执行的验收方式，例如测试、复现步骤、契约对比或行为检查；无法运行时要求给出验证方案。 |

按场景补足关键内容：

- **方案设计**：确实存在选型问题时再要求比较方案；说明权衡、受影响的契约和待确认假设。
- **功能实现**：指出现有接口与行为，要求聚焦改动，并给出相关验证。
- **故障排查**：提供现象和已有日志；要求分析引用证据，区分已确认根因与待验证猜测。
- **测试或审查**：指出要验证的行为或风险，要求结论附位置和证据。

当任务涉及选型或新增代码时，优先考虑项目已有实现、平台原生能力和现有依赖，再考虑新增抽象或依赖。这是按需使用的约束，不必机械加入每份提示词。

## 输出与自检

先用一个 Markdown 代码块给出完整提示词。代码块后只列用户必须补充的占位符或关键假设。若用户要求点评现有提示词，先简述具体问题，再给出改写版本。

输出前检查：提示词能独立使用；相关六要素已覆盖；项目事实有依据或明确标为未知；要求的验证证据可实际取得。不声称已运行测试，不伪造日志，不默认要求截图，也不要求输出隐藏推理过程。
